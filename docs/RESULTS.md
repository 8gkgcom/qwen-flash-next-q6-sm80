# 实测记录与解读

原生部署测试日期：2026-10-22。机器为 i5-12500T（6 核 12 线程）、96 GB RAM、双 CMP 170HX（各 64 GiB）、Ubuntu 22.04.5、内核 6.8.0-138-generic、驱动 610.57.04。去标识后的数据见 [reference/2026-10-22.json](../benchmarks/reference/2026-10-22.json)。其中保留题目编号、采样条件、时间、tokens 数和输出哈希，不包含主机地址、PID、GPU UUID 或原始输出。

## CPU 等待与元数据上传

CPU IPC 对照：调度进程约 96.8% → 6.4%，100% 表示一个逻辑核心。第一张卡对应的工作进程仍约占一个核心；消除调度空转不代表所有 CPU 瓶颈消失。三道题的生成速度基本不变。

异步 H2D 使用同一进程中的 baseline → async → baseline → async 顺序，每阶段三题，固定 temperature=1、xhigh、seed=42、512 tokens。

| 题目 | 原始 tok/s | 异步 tok/s | 相对变化 |
|---|---:|---:|---:|
| 任务队列与并发设计 | 63.54 | 64.94 | +2.20% |
| 数学证明 | 81.87 | 83.57 | +2.07% |
| Python TTL / LRU | 63.12 | 64.48 | +2.17% |

平均相对变化约 +2.15%，12 次文本哈希一致。这是固定条件下的短输入生成探针；没有统计置信区间，也未证明普遍的 2% 提升。

## 为什么保留 1024 预填充 / 0.96 显存预算

| 候选 | 历史观察 | 结论 |
|---|---|---|
| 8192 / 0.96 | KV 剩余约 1.98 GiB，小于 262K 所需约 3.51 GiB，启动失败 | 不采用 |
| 8192 / 0.99 | 能启动，32K 请求 OOM | 不采用 |
| 4096 / 0.99 | 能启动，32K 请求 OOM | 不采用 |
| 4096 / 0.98 | 混合请求 OOM | 不采用 |
| 4096 / 0.97 | 单个约 262K 检索通过，双 32K 请求 OOM；短请求等待明显增加 | 不采用 |
| 2048 / 0.96 | 启动、32K 与混合请求通过，单请求生成无提升 | 恢复 1024 |

2048 对照三题的平均生成变化约 **−0.0017%**，处于噪声量级。32K 首 token 从 **26.02 → 26.68 秒**；长请求期间短请求的总耗时从 **4.02 → 10.64 秒**。2048 没有完成完整 262K 压力验证，因为有限测试已没有性能收益，按回退条件恢复基线。

这些预填充/容量探针使用 **temperature=0、关闭思考**，与 temperature=1 的短输入生成测速是两类实验。不能把它们合并成同一“代码速度”数字。

## 不能从这些数字推导的结论

- 固定 512-token 输出往往还停留在 reasoning，没有可执行的最终代码；不能据此算代码通过率、比较模型智力或认定最佳温度。
- tokens/s 以首个到最后一个非空 SSE 文本增量的时间和 usage 计数近似计算；MTP 可能一次发送多个 token，属于客户端流式估计，不是内核级严格计时。
- 上下文窗口是输入加输出。单个长请求通过不表示两路完整 262K 同时可用。
- 简单非思考短题、复杂思考题、不同量化和不同硬件拓扑不能直接比较。
- 这份历史记录不表示新的 Docker 安装已经完成干净环境验证。
